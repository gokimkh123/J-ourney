# server — 백엔드·AI 서버

- 담당: 김건한
- 범위: REST API, WebSocket 이벤트 중계, AI 회의 엔진(페르소나 생성·자료조사·회의·확정 투표 집계)
- 설계 원칙: 판단은 LLM, 계산·검증은 코드, 최종 결정은 사람 4명 (요구사항·연동 명세서 v2.3)
- 배포: Docker 이미지 (GitHub Actions가 main 병합 때 빌드하여 GHCR에 저장). 개발·시연 서버는 학교 VM(Ubuntu, Docker)에서 docker compose로 실행하고 Cloudflare 터널로 공유함. 서버는 한 번에 한 컴퓨터에서만 켬 (DB마다 하루 API·LLM 상한을 따로 세기 때문)
- 실행: `.env.example`을 참고해 `server/.env`를 만든 뒤 `server` 폴더에서 `docker compose up -d --build`를 실행함 (서버·PostgreSQL·터널). 공유 주소는 `docker compose logs tunnel | grep -o 'https://[a-z0-9-]*\.trycloudflare\.com'`로 확인하며, 터널을 다시 시작할 때마다 바뀌므로 저장소에 적지 않음
- 장소 자료: 한국관광공사 TourAPI의 장소·연관 관광지·코드표(법정동 지역·장소 분류)를 PostgreSQL에 저장해 회의 후보 찾기에 사용함. 자료를 모으는 도구와 모은 자료는 저장소에 포함하지 않음. 장소 정보 출처 표시: ⓒ한국관광공사
- 회의 엔진 시험: `http://localhost:3000/dev/meeting`에서 1–15단계를 하나씩 실제로 실행해 봄 (1 준비 · 2 후보 찾기 · 3 고르기×4 · 4 후보 보드 · 5 사람 확인 · 6 동선 짜기 A·B · 7–12 평가·집계·수정·사회자 라운드 · 13 마무리 · 14 사람 선택·고치기 · 15 확정, 10/29 모두 구현). 시험용 경로는 서버 컴퓨터 안에서만 열리고 터널로 들어온 요청은 403 (팀원 확인 기간에만 `DEV_UI_TUNNEL=true`로 허용하며, 접근 키가 하나도 없으면 켜도 열지 않음)
- 관리자 모니터 (10/29): `http://localhost:3000/dev/monitor` — 앱이 보내는 요청(시각·주소·결과·걸린 시간·누가·기기)·WebSocket 열림·닫힘(닫힌 까닭·afterSeq)·주소별 1분 횟수·오늘 AI·카카오·관광공사 호출 수·진행 중 회의를 2초마다 보여 줌. 서버 컴퓨터(ssh로 연 로컬 주소)에서만 열리고 터널로는 팀 키가 있어도 403. 기록은 서버 메모리의 최근 500개뿐이며 토큰·접근 키·초대 코드·IP 원문은 두지 않음 (`src/lib/monitor.ts`)
- 회의 API (명세서 4.4·5장): 방장이 `POST /trips/{tripId}/meetings`로 시작하면 바로 202를 돌려주고 회의는 뒤에서 진행함 (여행 상태 meeting). 상태는 `GET /meetings/{meetingId}`, 놓친 이벤트는 `GET /trips/{tripId}/events?afterSeq=`. 여행마다 실행 횟수 상한(`MEETING_RUNS_PER_TRIP`, 기본 3회)을 넘으면 409 `MEETING_LIMIT`, 방장 포함 2명이 안 되면 409 `NOT_ENOUGH_MEMBERS`. 서버가 다시 켜지면 실행 중이던 회의는 실패로 바꾸고 여행 상태를 준비 중으로 되돌림 (사람 확인을 기다리던 회의는 그대로 이어 감)
- 접근 키 (`ACCESS_KEYS`): 값이 있으면 터널로 들어온 요청은 맞는 키를 낸 경우만 실제 API를 씀 — 회의 시작은 키마다 정한 횟수까지(넘으면 409 `ACCESS_QUOTA_EXCEEDED`), 키가 없거나 틀리면 403 `ACCESS_KEY_REQUIRED`, 성향 카드는 키가 없으면 규칙 카드. 앱은 요청 헤더 `X-Access-Key`, 시험 화면은 `/dev/key`에서 키를 넣으면 HttpOnly 쿠키로 기억함. 키로 시작한 회의·카드는 `LLM_REPLAY=true`여도 `ACCESS_LLM_REPLAY`(기본 fill: 녹화된 답은 다시 쓰고 없는 요청만 LLM) 모드로 LLM을 씀. 서버 안에서 보낸 요청(SSH 포트 연결)은 예전과 같고, 값이 비면 잠그지 않음. 키 원문은 서버에 두지 않고 `이름:횟수:sha256(키)`만 둠
- 실시간 연결: `wss://{host}/api/v1/trips/{tripId}/ws?token={token}&afterSeq={n}` (WebSocket, 서버 → 앱만). 접속하면 afterSeq 뒤 이벤트를 먼저 보내고 새 이벤트를 이어서 보냄, 25초마다 ping, 토큰이 없거나 다른 여행이면 연결하지 않음, 구성원당 연결 2개까지(넘으면 가장 오래된 연결을 닫음). 앱 → 서버 요청은 REST로 보냄 (앱이 WebSocket으로 보내는 글은 받지 않으며, 1KB를 넘는 글은 연결을 닫음)
- 5단계 사람 확인: 4단계 안건 중 장소 안건(⚠·✕가 붙은 곳·여행지 밖)이 있을 때만 LangGraph `interrupt()`로 멈추고(상태는 Postgres 체크포인트), 각자 `POST /meetings/{id}/review`로 안건마다 남김·뺌을 냄. 안건마다 다수결, 같으면 방장의 응답. 시간 제한 없이 4명이 모두 내면 자동 마감, 방장 `POST /meetings/{id}/review/close`('진행')는 안 낸 사람을 남김으로 셈 (사용자 결정 10/19). LLM 0회
- 6단계 동선 짜기 A·B: 4단계 반응·5단계 사람 확인 결과로 두 안을 짜 `plan.proposed`로 보냄. 머무는 시간·시각표는 근거가 없어 만들지 않고 들를 곳·순서·식당·가는 길만 줌 (사용자 결정 10/23). 하루 관광지 수는 참여한 사람(2–4명)마다 원하는 장소 수의 평균, 순서는 카카오 자동차 길찾기로 모든 순서를 비교해 이동이 가장 적은 순서, 점심은 관광지 절반 뒤·저녁은 마지막 관광지 뒤(꼭 지킬 식당 먼저, 그다음 동선에서 덜 벗어나고 성향 점수가 큰 식당, 그날 쉬거나 끼니 시간에 닫힌 곳은 뺌), 야경 좋아요가 있으면 해가 12° 진 때(항해박명 끝) 여는 전망대를 저녁 뒤 마지막에, 시작 시각이 모두 저녁 뒤인 행사도 저녁 뒤에 둠. B안은 꼭 지킬 곳·A안 1순위만 같이 쓰고 나머지는 다르게 (사용자 결정 10/19). 회의 조건의 `moveMode`(transit 대중교통·택시 / car 자차, 기본 transit)로 가는 길을 정함. LLM 0회 그날 쉬는 곳(휴무일)은 그날에 넣지 않고 다음 순위 곳으로 채우며, 꼭 지킬 곳은 여는 날로 옮김 (10/27 사용자 결정)
- 7단계 평가 1라운드: 사람마다 LLM 1회(4명 동시에)로 A·B 입장(찬성·조건부·반대)·이유·한마디·고칠 요청(최대 2개)을 받아 `round.started`·`agent.message`·`vote.cast`로 보냄. 답 형식표가 입장·요청 종류(넣기·빼기·바꾸기·긴 이동 줄이기)·장소(그 회의 표의 번호만)를 보기로만 받고, 코드는 고른 값과 코드가 계산한 사실표만 확인함(못 지킴·바꿀 수 있는 이동 기준 넘음인데 찬성 → 조건부, 꼭 지킬 곳·숙소·5단계에서 사람이 남긴 곳(표에 '바꿀 수 없음'으로 적음)을 빼자는 요청은 버림, 조건부·반대인데 요청이 없으면 규칙 요청). 6단계 안 메모는 AI 입력에 넣지 않음(이미 뺀 곳의 이동을 그 안의 이동으로 읽음, 10/28 실제 시험). AI가 쓴 글은 화면에 보이기만 하고 판단·점수에 쓰지 않음 (10/28 사용자 지시). 만족도(0–10)는 코드가 계산하며 AI는 점수를 내지 않음. 형식이 2번 틀리거나 LLM을 쓸 수 없으면 사실표 점수로 규칙 평가
- 2단계 후보 거르기 (10/27 사용자 결정): 여행지로 가는 곳이 아닌 시설의 공식 분류(`RETRIEVE.notDestinationCodes`: 사후면세점·대형마트·공연장·영화관·컨벤션센터·문화원·도서관·학교·경기장·수련시설·교통시설·골프장)는 후보에 넣지 않음(누군가 꼭 지킬 것으로 고른 곳은 넣음). 장소 이름으로 찾는 꼭 지킬 것은 이름이 같은 곳 중 관광지가 있으면 숙소·가게(`RETRIEVE.businessCodes`, 이름에 같은 낱말이 든 펜션·매장 등)는 꼭 지킬 곳으로 보지 않고, 이름 맞추기 LLM에 보여 주는 후보에서도 숙소·가게를 뺌
- 먹는 것 (10/27 사용자 결정): 알레르기·못 먹는 음식·식단은 사람마다 끝이 없어 성향 카드의 조건(꼭 지킬 것·바람)으로 받지 않음. 예전 카드에 남은 피할 음식 규칙도 후보·식당·AI 반응에 쓰지 않음. 식당은 14단계에서 사람이 끼니 식당을 바꿈 (`POST /trips/{tripId}/plan/edits`의 `meal`, 꼭 먹고 싶은 음식은 그대로 꼭 지킬 것)
- 카카오 길찾기 (6단계): 구간마다 카카오 값을 그대로 씀 (걸어갈 거리면 도보, 대중교통이면 카카오 추천 경로 + 택시 선택지, 대중교통이 없거나 누군가의 한 번 이동 상한을 넘고 택시는 안 넘으면 택시, 자차면 자동차). 무료 한도 안에서만 씀(결제 수단 없음): 기능별 하루 상한(`KAKAO_TRANSIT_DAILY_LIMIT`·`KAKAO_WALK_DAILY_LIMIT` 기본 1,000, `KAKAO_CAR_DAILY_LIMIT` 기본 3,000)을 `tour_api_usage`로 세고, 같은 구간은 `route_cache`에 7일 저장해 다시 쓰고(7일이 지난 것은 매일 지움, 회의 안에서는 같은 구간을 한 번만 물음), 회의 1번에 300회까지 부름. 화면에 넘기는 길찾기 링크는 https 카카오맵 주소만 씀. 한도·오류·교통 장애인 구간은 시간 없이 직선거리만 보냄(`source: estimate`). 키가 없으면 저장된 구간만 씀
- 4단계 반응: 분류·혼잡·영업시간·하루 시간은 코드 규칙으로, 사람이 쓴 말(바람·꼭 지킬 것·야경·오래 걷기·비싼 곳)은 AI가 다른 AI가 고른 곳의 소개글을 읽고 장소마다 충족(👍)·충돌(⚠)·언급 없음으로 가름 (생각 켬). 충족·충돌은 장소 글의 구절(근거)과 바람 글을 그대로 옮겨야 하고, 코드가 두 근거를 확인한 것만 받음 (사용자 결정 10/19, 설명문 구조는 10/19 근거 조사·비교 시험으로 정함). 바람 글이 없는 사람은 부르지 않음. 코드와 AI 중 더 무거운 반응을 남기고 ✕는 코드 규칙만 붙임
- 8–12단계 라운드 (10/29): 평가(7·11) → 집계(8·12) → 수정(9) → 사회자(10)를 최대 `maxRounds`까지 되풀이하는 LangGraph 고리(`src/meeting/rounds.ts`, 규칙 값 `ROUNDS`). 집계: 안마다 구성원 만족도 평균 ≥ `aiMinSatisfaction`(기본 7)이면 통과(가장 낮은 사람 조건 없음, 10/26 결정). 수정: 통과 못 한 안의 요청만, 그 안의 만족도가 낮은 사람 것부터, 안마다 라운드당 3개·같은 요청은 회의에서 한 번·한 라운드에 같은 곳은 한 번, 숙소·5단계에서 사람이 남긴 곳·그 꼭 지킬 것을 채우는 하나뿐인 곳은 그대로, 빼기·긴 이동 줄이기는 하루 최소 장소 수(2) 아래로 빼지 않음 → 바뀐 안만 6단계 계산(카카오 길찾기, 저장된 구간·이 회의에서 못 쓴 구간은 다시 부르지 않음, 회의당 상한은 라운드까지 누적)으로 다시 짜 같은 `planId`에 `version`을 올려 `plan.proposed`(`changes[]`)로 보냄. 사회자: 통과 못 한 안에 조건부·반대를 낸 AI + 고친 뒤 자기 꼭 지킬 곳·좋아하는 곳이 빠진 AI만 다시 평가(LLM)하고, 나머지는 지난 입장을 그대로 두고 만족도만 바뀐 일정으로 다시 계산(`vote.cast`의 `carried`). 끝나는 때: 둘 다 통과(남은 요청이 있으면 1번 다듬어 보고 평균이 떨어진 안은 되돌림, 10/19 결정) · 최대 라운드 · 통과 못 한 안의 평균이 2라운드 연속 오르지 않음 · 반영할 요청 없음 → 모두 그때의 A·B를 사람에게 넘김(실패 이벤트 없음). 실행 한 번의 노드 수 상한 `MEETING_STEP_LIMIT`(LangGraph 기본 25면 5라운드에서 실패) · 검증29(10/29, 여행 52개) 뒤 고침: '바꿀 수 없음' 곳을 가리킨 요청(표시가 있어도 66건): 답 형식표 설명에 쓰지 말라고 적고, 긴 이동 줄이기면 그 안에서 줄일 수 있는 가장 긴 이동으로 바꿔 반영(보기에서 번호를 빼 보니 AI가 그 번호를 고집해 형식 오류가 남) · 2라운드부터 평가 표에 '새로 들어옴' 표시와 사실 칸 '지난라운드뒤'(바뀜·그대로)를 코드가 붙임(바뀐 안을 두고 지난 이유를 그대로 쓰는 일) · 넣기로 그날이 다 차면 AI가 덜 고르고 점수(반응·좋아요·인기도)가 낮은 곳부터 밀려남(좋아요가 분류 코드로만 잡혀 명소가 먼저 밀려나던 일)
- 13단계 마무리 (10/29): 회의 끝에 두 안의 이름(12자)·한 줄 설명(40자)만 LLM 1회(형식이 틀리면 1번 더, 못 쓰면 'A안'·'B안', 두 이름이 같으면 B만 기본값, `src/meeting/finalize.ts`의 `FINALIZE`). AI가 쓴 글은 길이·칸 이름만 확인하고 화면에 보이기만 함. 만족도·평균·통과는 마지막 라운드 값, 양보(사람마다 그 안에서 못 지킨 꼭 지킬 것·⚠ 걸리는 곳)는 코드가 정리 → `meeting.agreed` → 여행의 일정 표(`trip_plans`, 0015)를 열고 공식 경로 여행은 상태 `voting`(이때부터 회의를 다시 시작하면 409 `MEETING_IN_PROGRESS`)
- 14·15단계 사람 선택·고치기·확정 (10/29, `src/meeting/choose.ts`·`src/routes/plan.ts`, 명세서 4.5): `GET /trips/{tripId}/plan`(일정 표) · `POST /plan/choice`(A·B 고르기, 모두 고르면 다수결, 2:2면 방장이 고른 안) · `POST /plan/choice/close`(방장 '정하기') · `GET /plan/options`(넣을 관광지·끼니마다 바꿀 식당) · `POST /plan/edits`(빼기·넣기·다른 날로·순서·끼니 식당, 고른 값만, 한 번에 10개) · `POST /plan/confirm`(방장, 확정 투표 시작) · `POST /plan/votes`(찬성·반대). 고칠 때마다 6단계 계산(카카오 길찾기, LLM 0회)으로 다시 짜 같은 `planId`에 `version` + 1로 `plan.proposed`(`changes[]`)를 보냄. 숙소는 바꾸지 않고, 사람이 정한 순서·끼니 식당은 그대로 둠. 동시에 고치면 먼저 저장한 쪽만(늦은 쪽 409 `PLAN_LOCKED`). 확정 투표 중에는 고치지 않으며, 모두 찬성하면 확정(`plan.confirmed`, 여행 상태 `confirmed`), 한 명이라도 반대하면 다시 고치기(`confirm.closed`). 재회의·수정 요청 문장은 없음 (10/14 결정). 고칠 때 6단계 재료를 회의 체크포인트에서 읽으므로, 고르거나 고치는 중인 일정 표의 회의 기록은 30일 정리에서 남김
- 회의 엔진 LLM 사용: 회의 1번에 고르기 4–5회(AI 4명) + 이름 맞추기 0–3회(꼭 지킬 것·꼭 피할 것에 장소·음식 이름이 있을 때 6개씩 1번, 구 단위 여행에서 여행지 안에 없으면 같은 시·도의 다른 구·군으로 1번 더) + 4단계 반응 0–4회(다른 AI가 고른 곳이 있고 바람 글이 있는 사람마다 1회), 5·6단계는 0회, 7단계 평가 4회(사람마다 1회, 형식이 틀리면 1번 더), 11단계 평가 2–5라운드는 사회자가 부른 AI만 1회씩(8–10·12단계는 0회) + 13단계 이름 짓기 1회(형식이 틀리면 1번 더), 14·15단계는 0회. 실행 1회 40회(10/29 30 → 40)·하루 500회 상한을 넘거나 실패하면 규칙 고르기·규칙 평가(시험 화면 '상한')·'찾지 못함' 메모로 대신함. Claude 지시문은 캐시해 입력 비용을 줄임
- LLM 녹화·재생: 실제로 부른 LLM의 답은 요청 지문(모델·용도·지시문·입력·시도 번호의 sha256)과 함께 `llm_records`에 녹화함. `LLM_REPLAY=true`이면 LLM을 부르지 않고 녹화된 같은 요청의 답 → 같은 여행의 지난 회의에서 AI가 고른 곳·이름 맞추기(조건이 같고, 그 회의 뒤에 성향을 바꾸지 않은 사람만, 고른 곳이 지금 후보에 모두 있을 때) → 같은 응답으로 AI가 만든 성향 카드 순서로 다시 쓰고, 없으면 규칙으로 대신함. `LLM_REPLAY=fill`이면 다시 쓸 것이 없는 요청만 LLM을 불러 녹화함(측정용). 다시 쓴 답은 LLM 횟수에 세지 않음 (기본값: 다시 쓰지 않음)
- 여행지 밖 꼭 지킬 곳: 구 단위 여행에서 꼭 지킬 곳이 여행지에 없으면 같은 시·도에서 찾아 '여행지 밖'으로 보드 안건에 올림. 편도 75분을 넘으면 메모로만 남김 (근거: 2012 국민여행실태조사 분석에서 관광 수요의 94.3%가 75.1분 안, 권영현·김의준 2015)
- 이름 맞추기 (10/29 사용자 결정 '가', `src/meeting/names.ts`): 꼭 지킬 것·꼭 피할 것의 장소·음식 이름(예: 돼지국밥, 해동용궁사, 우도 빼기)은 서버 코드가 글자로 맞추지 않고 LLM이 여행지 장소 목록에서 같은 곳의 번호를 고름(넣기 2곳·피하기 4곳까지). 코드는 LLM에게 보여 줄 목록을 줄일 때만 사람이 쓴 이름의 글자 겹침·인기 순을 씀. 설명문은 10/28 비교 시험(조건 109개, Haiku)의 92.0% 판 그대로(코드 글자 맞추기 먼저 87.2%). LLM을 쓸 수 없으면(하루 상한·오류·`LLM_REPLAY`에 녹화 없음) 맞추지 않고 메모 'AI 이름 맞추기를 하지 못해 적용하지 못함'. AI가 맞춘 곳은 5단계 사람 확인 안건이 아닌 4단계 메모로 보임(`REACT.nameMatchAgenda`). 6단계 끼니 보충 식당도 LLM이 고른 곳만 꼭 먹을 곳으로 봄. target이 없는 10/14 전 카드의 규칙은 쓰지 않고 메모
- 지역 조건·여행지 (10/29 사용자 결정, '사람이 자유롭게 쓴 글은 코드로 처리하지 않음'): 15번에서 나온 지역 조건(예: 서면 쪽 위주로)은 2단계에서 LLM이 여행지 시·도의 구·군 목록 또는 장소 목록에서 번호를 고름(`src/meeting/areas.ts`, 동네 → 그 동네가 있는 구·군, 특정 장소 → 그 장소, 회의당 0–2회). 방장이 쓴 여행지는 조건 저장 때 LLM이 전국 시·도·시·군·구 목록에서 고름(`src/meeting/destination.ts`, 1회, 구가 있는 시는 그 아래 구까지). 비교 시험(Haiku 그대로): 지역 조건 153개 예전 코드 80% → LLM 97%, 여행지 80개 예전 코드 63개 → LLM 80개. 여행지를 확인하지 못하면 503 `AI_UNAVAILABLE` — 접근 키가 있는 서버에서 키 없는 바깥 요청과 `LLM_REPLAY=true`에서는 녹화된 같은 여행지 글만 확인됨
- 1–7단계 점검 (10/28): 지역 넣기 규칙이 여행지 전체(모든 구·군)를 가리키면 조건으로 쓰지 않고 메모만 남김, 지역 규칙은 제외 시설을 끌어들이지 않음, 맞는 곳이 없는 피하기 규칙은 메모로 알림, 한 글자 음식(회·굴)은 글자 포함으로 맞추지 않고 이름 맞추기(LLM)로 넘김, 안건은 여행지 밖·이름 맞춤인 곳을 먼저 둠(상한에 잘리면 메모) · 6단계: 꼭 지킬 식당은 한 번만, 하루 관광지가 `SCHEDULE.orderAllMax`(8)곳을 넘으면 모든 순서 대신 가까운 곳부터 잇고 두 구간 바꾸기로 다듬음 · 7단계: DB에서 보충한 식당의 꼭 지킬 것 표시도 봄, '바꿀 수 없음'은 그 안에서 그 규칙을 채우는 곳이 하나뿐일 때만, 긴 이동은 6단계와 같은 잣대(그날 다른 관광지들에서 더 먼 쪽이 숙소·식당·못 바꾸는 곳이면 못 줄임), 👍·⚠는 같은 곳을 한 번만 셈 · 실행기: 멈춤·끝과 상태를 실행 흐름에서 받음(체크포인트를 다시 읽지 않음), 서버를 다시 켜 끊긴 회의도 `meeting.failed`를 남김
